# Roll & Pay — 要件整理

作成日：2026年10月14日

位置づけ：初期プロンプトと打ち合わせ内容を整理した、実装前の合意確認用資料。

この資料では、合意した利用形態とルールを中心に記載する。技術構成は採用候補として扱い、画面の詳細や未決定事項は試作・設計時に詰める。初期プロンプトと異なる点は、本資料の打ち合わせ内容を優先する。

## 1. 目的

友人・知人との食事や飲み会で、サイコロによって会計の端数を負担する人を決めるWebアプリケーションを作る。

敗者以外は同額を千円単位で敗者へ渡し、敗者が会計をまとめて支払うことで、参加者間の小銭のやり取りをなくす。ゲーム結果と金額を保存し、参加者ごとの累積負け額を振り返れるようにする。

個人利用と技術学習を目的とし、ランニングコストをできるだけ低く抑える。

## 2. 利用者と利用形態

- アプリを管理・利用するのは、原則として管理者本人一人。
- 管理者がログインした一台のスマートフォンを、参加者が一緒に使う。
- 参加者全員のログインやアカウント作成は不要。
- 参加者は、あらかじめ用意した固定の名前リストから選択する。
- ログインユーザーとゲーム参加者は別の概念として扱う。管理者自身も参加者として選択できる。
- 各自がサイコロを押す場合も、管理者のログイン状態のまま同じ端末を操作する。
- 参加者が各自の端末から同じゲームに接続する機能は、初期版の対象外。

初期の参加人数は、原案どおり2〜6人程度を想定する。正式な上限は画面の試作で確認する。

## 3. 認証とアクセス制御

### 合意した方針

- Microsoft Entra External IDは採用せず、既存のAzureサブスクリプションに紐づくMicrosoft Entra IDテナントを利用する方針とする。
- 管理者のみがアプリとAPIを利用できるようにする。
- 履歴閲覧にも認証と利用権限を要求する。履歴を一般公開する方針は取り下げる。
- ゲーム作成、抽選、金額登録、履歴取得のAPIは、すべて管理者の権限で呼び出す。
- 認証済みであることに加え、許可された管理者本人であることを確認する。
- スマートフォンのIPアドレスによる制限を、本人確認の手段にはしない。

### 設計時に確認すること

- 既存テナントと、普段利用しているアカウントの種類・所属。
- アプリ登録、ログイン方式、管理者の許可方法。
- MSAL.js等によるアクセストークン取得と、Azure Functions側での検証方式。

API認証にはIDトークンではなくAPI向けアクセストークンを利用する。クライアントから送られたユーザーIDだけでアクセスを許可しない。

参考：[Microsoft Entra IDのシングルテナント／マルチテナントアプリ](https://learn.microsoft.com/en-us/entra/identity-platform/single-and-multi-tenant-apps)

## 4. 基本的な利用の流れ

1. 管理者がログインする。
2. 固定の名前リストから、その日の参加者を選ぶ。
3. ゲームを開始し、参加者ごとの3Dサイコロを表示する。
4. 全員分を一括で振る、または同じスマートフォンで各自が自分のサイコロを押す。
5. 対象者全員の出目が確定したら、敗者を判定する。
6. 最小出目が同点の場合は、参加者全員で振り直す。敗者一名が確定するまで、全員での振り直しを繰り返す。
7. 敗者が決まったら会計総額を入力する。
8. 各自の負担額と負け額を確認し、結果を保存する。
9. 結果画面を見せる、または結果画像をLINEなどで共有する。
10. 後からゲーム履歴や累積負け額を確認する。

会計総額の入力タイミングは現時点では原案に沿っているが、UIの試作で変更してよい。

## 5. サイコロと敗者判定

### 基本方針

- 参加者一人につき、通常の6面サイコロを一個表示する。
- 最も小さい出目の参加者を敗者とする。
- 全員一括と個別の両方の操作を想定する。具体的なボタン配置は試作で決める。
- 個別操作の場合は、対象者全員が振り終わってから敗者を判定する。
- 一括・個別の操作が混在しても、同じ抽選が二重に実行されないようにする。
- 確定した結果を、任意の振り直しで上書きできないようにする。
- 本番の出目はバックエンドで確定し、フロントエンドは結果に合わせた3Dアニメーションを行う。
- 出目の数値と3Dサイコロの上面を一致させる。

### 同点時の確定ルール

最小出目が複数人いる場合は、同点者だけでなく、ゲームの参加者全員がサイコロを振り直す。前回の出目にかかわらず、全員が再び敗者の候補になる。

振り直した結果も最小出目が同点であれば、再び全員で振り直す。最小出目の参加者が一名になった時点で、その参加者を敗者として確定する。

## 6. 支払いと負け額の計算

### 確定したルール

会計総額を「参加人数 × 1,000円」で割った余りを、敗者の負け額として記録する。他の参加者は同じ金額を千円単位で負担し、敗者はその金額に負け額を加えた額を負担する。

金額は整数円で扱う。

```text
T：会計総額（円）
N：参加人数
B：通常の一人分（千円単位の基準負担額）
L：負け額

B = floor(T / (N × 1,000)) × 1,000
L = T - B × N

敗者以外の一人当たり負担 = B
敗者自身の負担           = B + L
敗者が他の人から受け取る合計 = B × (N - 1)
```

ここでいう「通常の一人分」は、千円単位で切り捨てた基準額であり、会計総額を単純に人数で割った均等割り額とは異なる。

### 例：13,800円を4人で支払う場合

| 項目 | 金額 |
|---|---:|
| 千円単位の基準負担額 | 3,000円 |
| 敗者以外の一人当たり負担 | 3,000円 |
| 敗者が他の3人から受け取る合計 | 9,000円 |
| 敗者自身の負担 | 4,800円 |
| 記録する負け額 | 1,800円 |
| 会計総額 | 13,800円 |

**累積負け額に加算するのは1,800円であり、敗者自身の負担4,800円ではない。** また、厳密な均等割りとの差額である1,350円も、今回の負け額には使わない。

会計総額が「参加人数 × 1,000円」で割り切れる場合、負け額は0円となる。

会計総額が「参加人数 × 1,000円」未満の場合、この計算では他の人の負担が0円、敗者の負担が会計全額となる。この境界ケースをそのまま採用するかは、確認事項として残す。

## 7. 履歴と結果共有

### 履歴

保存・参照する情報は、以下を基本とする。

- ゲーム日時。
- 参加者と、ゲーム当時の表示名。
- 各抽選の対象者と出目。同点による再抽選も記録できる構造を想定する。
- 最終的な敗者。
- 会計総額、千円単位の基準負担額、各参加者の負担額、負け額。
- 金額の登録日時。

参加者ごとの累積負け額を確認できるようにする。参加回数、敗北回数、平均負け額などの追加統計は、将来機能として扱う。

履歴は管理者の認証後に表示する。2026年10月14日の画面確認で、ホームは参加者ごとの累積負け額を表示し、ゲーム履歴は別の履歴画面にまとめる方針とした。履歴はサイコロの記録より、誰が・いつ・いくら負けたかを中心に表示する。

履歴の個別詳細から削除できる機能を追加する。削除した記録の負け額は累積からも除外する。削除方式・復元可否・APIとデータの整合性は後続の基本設計で決める。任意の振り直しや保存後の金額訂正は、この追加要望では採用しない。

### 共有

参加者にログインしてもらう代わりに、結果を画像などで共有できることを目指す。

- 参加者、出目、敗者、各自の負担額が一枚でわかる結果画面を想定する。
- まずはスマートフォンのスクリーンショットで共有できる見た目を検討する。
- アプリからの画像保存・共有ボタンは追加候補。初期版に含めるかは試作で判断する。
- LINEなどへの送信は、管理者自身が行う利用形態を想定する。
- 公開履歴ページや、ログイン不要の結果閲覧URLは現時点では要件に含めない。

## 8. UIの方向性

- スマートフォンでの利用を優先する。
- 参加者とサイコロの対応が明確で、出目を読み取りやすい画面にする。
- 一括操作と個別操作をわかりやすくする。
- アニメーション中・他の人の操作待ち・再抽選・敗者確定を区別して表示する。
- 会計総額、各自の負担額、記録する負け額を混同しない表示にする。
- 3D表現は視認性を優先し、工場設備や特殊な背景演出は行わない。

画面モックは、ログイン、ホーム、参加者選択、サイコロ、金額確認／結果、負け額の履歴／詳細で構成する。2026年10月14日に初版の画面デザインを一旦確定し、同日の追加要望でホームから履歴を分離し、履歴削除を追加した。詳細は `spec/screen-mockups.md` を参照する。

## 9. 技術構成の候補

初期プロンプトの技術構成を基本候補として維持する。導入前にバージョン、Azureの対応状況、費用、構成上の制約を確認する。

| 領域 | 候補・方針 |
|---|---|
| フロントエンド | Vite、Vanilla TypeScript、HTML／CSS。初期段階ではReact等を使わない |
| 3D描画 | Three.js |
| アニメーション | GSAP。初期段階では物理演算エンジンを使わない |
| バックエンド | C#、.NET 10、Azure Functions 4.x、.NET Isolated Worker、HTTPトリガー |
| 通信 | REST API、JSON |
| 認証 | 既存Microsoft Entra IDテナント。MSAL.jsを候補とする |
| データ保存 | Azure Cosmos DB for NoSQL |
| フロントエンド配置 | Azure Static Web Apps Freeを候補とする |
| API配置 | 独立したFunction App。Consumption／Flex Consumptionの適合性を確認する |
| 開発環境 | Windows、VS Code、Node.js／npm、.NET SDK、Azure Functions Core Tools、Git |

Docker、Docker Compose、WSL、Visual Studioは必須にしない。単一Gitリポジトリで管理し、過度な抽象化や階層化は避ける。

## 10. 品質上の要件

- 抽選と金額登録の重複実行を防ぐ。
- 通信失敗や再読み込み後も、確定済みの結果を誤って再抽選しない設計にする。
- 会計総額や参加人数の入力を検証する。
- サイコロの結果、敗者判定、金額計算、3Dの上面との一致を検証する。
- APIで認証と管理者の利用権限を検証する。
- TypeScript strict、C# Nullable Reference Typesを有効にする。
- 接続情報や秘密情報はソースに埋め込まず、トークンや秘密情報をログに出さない。
- CORS設定とXSS対策を行う。
- ローカルで画面を確認できるようにする。

3. 会計総額が「参加人数 × 1,000円」未満の場合の扱い、0円や金額上限の扱い。

6. ゲーム履歴の並べ方。累積負け額はホームに表示する。

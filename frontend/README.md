# Roll & Pay — フロントエンド

Vite + Vanilla TypeScriptで初期化。React等のUIフレームワークは使用しない。

## 開発

Node.js 22.12以降とpnpm 11.25.0を使用する。今回の検証環境はNode.js 24.19.0。

### 初回の環境準備（Windows）

Codex内部のNode.js・pnpmは通常のPowerShellのPATHには追加されない。自分のターミナルで使用するため、開発用のNode.jsとpnpmを用意する。

1. [Node.js公式サイト](https://nodejs.org/en/download)からNode.js 24系のWindowsインストーラーを取得してインストールする。
2. PowerShellを開き直す。VS Code内のターミナルの場合はVS Code自体を再起動する。
3. 次のコマンドを実行する。`.cmd`を指定するとPowerShellのスクリプト実行ポリシーの影響を避けられる。

```powershell
node --version
npm.cmd --version
npm.cmd install --global pnpm@11.25.0
pnpm.cmd --version
```

`pnpm` が認識されない場合はターミナルを再起動して確認する。PowerShellでは以下の `pnpm` コマンドを `pnpm.cmd` として実行してもよい。

参考：[pnpm公式のインストール手順](https://pnpm.io/installation/)

リポジトリのルートから：

```powershell
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

ターミナルに表示されるURLをブラウザーで開く。開発サーバーは既定ではローカル向け。

## 確認・ビルド

```powershell
pnpm typecheck

```

`build` はTypeScriptの確認後、静的ファイルを `dist/` に出力する。`preview` はビルド済みファイルのローカル確認用。

## ディレクトリと役割

- `index.html`：日本語ページの入口。
- `src/main.ts`：起動入口。
- `src/app.ts`：ページの組み立て、ログイン状態の反映、画面の破棄。
- `src/router.ts`：ハッシュルーティング。直接リンク・再読み込み・戻る／進むに対応。
- `src/state.ts`：選択参加者・保存前の金額入力。ゲームの正本はサービスに置く。
- `src/pages/`：ログイン、ホーム、参加者選択、サイコロ、金額入力／結果、履歴、履歴詳細／削除確認。
- `src/components/`：ヘッダー、参加者リスト、支払い結果、サイコロ描画、DOM・操作の共通処理。
- `src/domain/`：型、敗者判定、金額入力検証・計算。
- `src/services/game-service.ts`：画面が依存する操作のインターフェース。
- `src/services/mock-service.ts`：ブラウザー内のデモ用ゲーム操作・保存。
- `src/services/api-client.ts`：API通信、トークン再取得、読取セッションの継承。
- `src/services/api-service.ts`／`api-models.ts`：実API操作と画面用データへの検証・変換。
- `src/services/runtime.ts`／`auth.ts`：モード選択、MSALログインと権限確認。
- `src/styles/`：基本スタイルと部品スタイル。
- `tsconfig.json`：TypeScript strictを有効化。
- `pnpm-lock.yaml`：依存バージョンの固定。

## 実APIへの接続

G01〜G10の全業務APIに接続する。`frontend/.env.example`を`.env.local`へコピーし、以下を設定して開発サーバーを起動し直す。

```dotenv
VITE_APP_MODE=api
VITE_API_BASE_URL=https://<functions-host>/api/v1/
VITE_ENTRA_TENANT_ID=<tenant-guid>
VITE_ENTRA_SPA_CLIENT_ID=<spa-client-guid>
VITE_ENTRA_API_SCOPE=api://<api-client-guid>/access_as_user
```

これらはビルド時に埋め込む公開識別子。アクセストークンやクライアントシークレットは指定しない。未指定のモードは`demo`。`api`で設定不足の場合は起動／ビルドエラーにし、デモへ切り替えない。ローカルAPIは`http://localhost:7071/api/v1/`も利用可能。

SPA登録に`https://<画面ホスト>/redirect.html`と開発用`http://localhost:5173/redirect.html`をリダイレクトURIとして登録する。実際に使うポート・ホストと完全一致させる。MSAL v5の専用ページにはアプリ本体・ルーターを起動せず、COOPヘッダーも設定しない。[Microsoftのredirect bridge手順](https://learn.microsoft.com/en-us/entra/msal/javascript/browser/redirect-bridge)に従う。FunctionsのCORSには画面のOriginを登録する。Entra設定の準備は[インフラ手順](../infra/scripts/README.md)を参照。

| 画面操作 | 接続先・動作 |
|---|---|
| Microsoftログイン／再読み込み | MSALでAPI向けトークン取得後、A01 `GET /me`で管理者権限を確認 |
| ホーム・ゲーム再開 | A04 `GET /games/active`、A05 `GET /games/{id}`で最新状態を表示 |
| 参加者選択・作成 | A02 `GET /participants`、A03 `POST /games`。サーバーの名前・選択順を使用 |
| サイコロの個別／一括抽選 | A06 `POST /games/{id}/rolls`。サーバーの出目と敗者判定を表示 |
| 引き分け後の全員振り直し | A07 `POST /games/{id}/rounds`。全員が未抽選の次ラウンドを作成 |
| ゲーム中止 | A13 `POST /games/{id}/cancel`。ホームでの確認後に中止 |
| 金額プレビュー | A08 `POST /games/{id}/payment-preview`。サーバーの計算結果を表示 |
| 金額保存・結果表示 | A09 `POST /games/{id}/payment`。確認した総額・ETagで保存後、A05で最新の結果を取得 |
| 累積負け額 | A12 `GET /statistics/losses`。10進文字列をBigIntへ変換し、無効者を含む全員を表示 |
| 履歴一覧 | A10 `GET /games?limit=20`、さらに表示で不透明カーソルを送信 |
| 履歴詳細 | A15 `GET /games/{id}/history-detail`。当時の名前と負担額を表示し、抽選記録は取得しない |
| 履歴削除 | A14 `DELETE /games/{id}`。確認画面のETagで削除し、削除状態と最新累積額を取得 |

APIモードでは作成→個別／一括抽選→引き分け後の全員振り直し→敗者確定→金額プレビュー→保存・結果表示、未完了ゲームの中止、履歴参照・削除、累積負け額を利用できる。画面の名前・出目・敗者・会計・累積額はAPI応答を使う。デモの名前・履歴・金額を実API画面へ流用しない。

A12には参加実績の項目がないため、APIモードでは累積0円も「0円」と表示し、未参加とは判定しない。現在無効な参加者も累積額の対象に含め、名前に「現在は無効」を添える。デモの「— は未参加」という表示とは区別する。

抽選・振り直しは表示中のrevisionと現ラウンドを使い、保存はプレビューと同じ総額・ETag、中止は表示ゲーム、削除は履歴詳細の公開ETagを`If-Match`で送る。要求キー・本文・ETagは送信前にsessionStorageへ保持する。通信断後に同じ操作を押すと元の要求を再送し、別の操作への変更は結果確認まで止める。成功／再生後はA05を取得し直す。「最新の状態を確認」で新しいrevisionを確認できた場合は、古いIf-Matchの要求が再適用されないことが確定するため、未確認要求を解除する。409／412でも最新を取得するが、古い操作は自動実行しない。ホーム・抽選・金額入力・履歴詳細／削除確認には最新状態の確認ボタンを用意する。保存と削除では応答中の集計を検証したうえでA12も再取得し、再生された古い累積額を採用しない。保存成功の再生後にA05が410なら保存結果を表示せず、削除済みとして案内する。

作成前にUUIDキーと参加者順を`sessionStorage`へ記録する。通信断・503・再読み込み後は同じ本文・キーで再送し、成功後もA05で最新状態を取得する。未確認の作成があるときは参加者選択へ同じメンバーを復元し、異なる本文での送信を止める。ストレージへ要求を記録できない場合は作成要求を送らない。401では一度だけトークンを強制更新し、続く401や対話認証が必要な場合はログイン画面へ戻る。その他の更新の自動再送は行わない。

API通信は直列化し、`X-Read-Session`を次要求へ継承する。端末の読取セッションと未確認更新要求はAPI URL・SPA登録・アカウントごとに分け、ログアウト時に読取セッションを削除する。ゲーム本体・履歴を独自の永続キャッシュには保存しない。トークンはMSALのsessionStorageで管理する。

## デモで使える機能

`pnpm dev` で起動し、「デモをはじめる」から操作する。

- 固定6人の参加者選択、2〜6人での開始。
- ホームに全員の累積負け額。未参加は「—」、参加済み0円は「0円」。
- 個別抽選と未抽選者だけの一括抽選。同点は全員の次ラウンドへ。
- Three.js＋GSAPの3D表示。上面はサービスで確定した出目に一致。数値も併記し、WebGL不可時は数値表示で操作可能。
- 整数円の入力検証、負担額プレビュー、結果保存、共有用表示。
- 負け額の履歴一覧・詳細、削除確認、削除額の累積からの除外。
- 再読み込み後のゲーム復元、ホームからの再開・中止。
- 保存失敗・競合時のエラー表示、送信・アニメーション中の重複操作防止。
- 抽選・振り直しなど同じ画面の更新ではスクロール位置を保持。別画面への遷移は先頭を表示する。

初回は仮データ4件を登録する。ゲーム記録は `localStorage` の `roll-and-pay.demo.v1`、デモセッションは `sessionStorage` に保存する。本番の認証・API・DBには接続しない。個人情報や本番の記録を入力する用途にはまだ使わない。

デモ記録はホームの「デモデータの管理」から、確認操作を経て初期サンプルへ戻せる。通常の履歴削除は状態を削除済みにして一覧・累積から除外し、初期化まで内部記録を保持する。

## デモで仮採用したルール

機能設計B01〜B10をもとに、人数2〜6人、未完了ゲーム1件、総額1〜9,999,999円、少額会計は敗者の全額負担を採用した。保存後の金額訂正・任意の振り直し・削除の復元は用意していない。

「参加済み」はゲームを開始した時点で判定し、中止・削除後も維持するデモ上の方針。確定する本番仕様は後続で調整する。累積額は削除されていない完了ゲームの負け額だけを合計する。

デモは通常の直列操作と版番号の照合に対応するが、複数タブの完全なトランザクション保証は持たない。本番の再送保証・排他制御はバックエンドの冪等性キー・ETag・DBトランザクションで行う。

## 実環境での確認

`VITE_APP_MODE=api`と接続先の公開識別子を設定し、実Entra・Functions・Cosmosを使ったログイン、作成・抽選・金額保存、履歴参照・削除、累積額更新、中止・再開を確認する。実端末でのポップアップ許可、リダイレクトURI、CORS、再読み込み後の復元も対象とする。自動テストはAPI契約に沿ったHTTP応答を使用し、実テナントの疎通を代替しない。

Three.js・GSAPはサイコロ画面で遅延読み込みする。現在の3Dチャンクは約600KB（gzip約160KB）で、Viteの500KB注意表示が出る。初期画面とは分離済みで、実端末での読込・描画速度の調整は今後行う。
